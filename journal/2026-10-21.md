## 代理链路（本次最大障碍，已打通）

GitHub 访问在当前环境要走代理，且有两层坑：

| 层 | 问题 | 解法 |
|---|---|---|
| WorkBuddy 透明代理 | 环境变量被注入 `HTTP_PROXY=http://127.0.0.1:62710`，直连 github.com 时 CONNECT tunnel 502 | 覆盖环境变量指向自建转发层 |
| .NET (GCM) | `ServicePointManager 不支持具有 https 方案的代理`——只认 http 方案 | 自建 http→https CONNECT 转发层 |

**关键事实**：
- `api.github.com` 直连 **200 正常**，但 `github.com` 直连 **超时**。设备流和网页端打的是 github.com，必须走代理。
- 系统代理注册表残留 `ProxyServer='https=fan.596189.xyz:443'`（`ProxyEnable=0`），`.NET` 仍会读它 → 改成 http 方案即可。
- `reg.exe` 被沙箱黑名单拦截，读注册表要用 Python `winreg`。
- Windows 无 `pty` 模块（`termios` 缺失），GCM 的 device flow 无法通过伪终端显示验证码 → 改为直接调 GitHub Device Flow API（`client_id=0120e057bd645470c1ed`），完全可控。

**自建转发层**：`~/.workbuddy/tools/local_proxy.py`（原 `D:/360Downloads/2026-10-21-14-01-54/local_proxy.py`）
- 用法：`python local_proxy.py --listen 127.0.0.1:8899 --upstream fan.596189.xyz:443`
- 关键点：上游是 https 代理，**必须先 TLS 握手再发 CONNECT**，否则连不通。
- 用途：把 .NET 只认 http 方案的限制绕开；同时 git push 也需要它（直连被透明代理拦）。

## UIA 自动化 GitHub 设备授权（技术要点）

Windows 上没有 GitHub 连接器/gh CLI/SSH key，最终走 **GitHub Device Flow API + UIA 驱动已登录的 Chrome**。

**必须记住的几个坑**：
1. **UIA SetValue 对 React 受控输入框无效** —— 值写进去了但 React state 没更新，提交后 GitHub 报"糟糕，我们什么也没找到"。必须用 `SendInput` + `KEYEVENTF_UNICODE` 真敲字符。
2. **设备页刷新后 UIA 元素引用立刻失效** —— 每步都要重新 `FindAll` 枚举，不能跨步骤复用 element 对象。
3. **omnibox 会自动补全成 `?user_code=XXXX` 的旧地址** —— 粘贴 URL 后必须按 `Delete`(0x2E) 消掉补全后缀再回车。
4. **SetForegroundWindow 跨进程会被前台锁拦** —— 需 `AttachThreadInput(cur_tid, fg_tid, True)` 绕开。
5. **GitHub 设备码是 8 个分格输入框**（`user-code-0..3, 5..8`，第 4 位是中间的 `-`），聚焦第一个后连敲会自动跳格。
6. **点击按钮要用鼠标事件**，`InvokePattern` 对 GitHub 的 `<button class="btn btn-sm btn-primary">` 不可靠 —— 取 `CurrentBoundingRectangle` 中心点 + `mouse_event` 点击。
7. **2FA 会话验证页**标题是"验证会话"，有「继续使用 <账号>」按钮，点击后回到设备页。
8. `GlobalAlloc` 在 **kernel32** 不是 user32；`ProxyEnable` 注册表值是 **REG_DWORD** 不能用 REG_SZ 写。

**UIA 控件类型是整数枚举**（`EditControl`=50004、`ButtonControl`=50000），不能按字符串比对。
